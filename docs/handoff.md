# ライブ配信音声エフェクト Chrome拡張 引き継ぎメモ

最終更新：2026-11-11（拡張 v0.13.0）

## 目的

ライブ配信の音声に、リアルタイムでイコライザーとノイズキャンセルをかけるブラウザ拡張（Manifest V3）を作る。ChromeとFirefoxに対応する。

- 対象サイト
  1. ニコニコ生放送（必須）：対応済み
  2. YouTube（ライブと通常動画の両方）：対応済み
  3. Kick：対応済み
  4. Twitch：対応済み
  5. TVer（見逃し配信とリアルタイム配信）：対応済み
  6. ABEMA（放送中のチャンネルとビデオ）：対応済み

## 方針（2026-11-10に決めたこと）

- **対象サイトは限定し、主要な動画サイトを1つずつ足す**（次の候補は「次のサイトの候補」を参照）。すべてのサイトで有効にすることはしない
  - 理由：サイトが自前で`createMediaElementSource`を使っていると、先に接続してサイトのプレイヤーを壊すおそれがある。DRM付きの動画で無音になるおそれがある（ABEMAのDRMでは音が取れたが、すべてのDRMで取れるかは分からない）。SNSのタイムラインなどで多数の動画に接続してCPUを使う。全サイトの権限は警告が強く、公開時の審査も厳しい
- **当面は自分用。形が整ったら一般公開も考える**（「公開に向けて」を参照）
- **Firefoxにも対応する**（「Firefox対応」を参照）

### 使い方

- Chrome：`chrome://extensions`でデベロッパーモードをオンにし、「パッケージ化されていない拡張機能を読み込む」で`extension/`フォルダを選ぶ
- Firefox：`about:debugging`の「このFirefox」→「一時的なアドオンを読み込む」で`extension/manifest.json`を選ぶ。Firefoxを再起動すると消える
- 拡張アイコンのポップアップで、次の設定を変える
  - 全体のON/OFF。OFFのあいだは、ほかの欄は薄く表示され、操作できない（OFFのあいだは変えても音が変わらないため）
  - ノイズキャンセルのON/OFFと方式（RNNoise / DeepFilterNet3）
  - 音量をそろえる強さ（オフ / 弱 / 中 / 強）
  - EQ：見出しの横のドロップダウンで、カスタムかプリセットを選ぶ
    - 10バンドのゲインは±12dB。画面では高音が上
    - プリセットを選ぶとその値がスライダーに入り、スライダーを動かすとカスタムになる
  - オート（試作）：EQの見出しの下のスイッチでオン・オフする。オンのあいだは補正の強さ（控えめ / 標準 / 強め）を選べる
    - オンのあいだは、ドロップダウン・スライダー・「フラットに戻す」を操作できない。スライダーには自動で決めた補正量を表示する
    - オフに戻すと、オンにする前の手動のEQ（カスタムかプリセット）に戻る
- ポップアップの高さは、通常554px、オートのとき590px（Chromeのポップアップは600pxまで）。項目を足すときは超えないか測る
- 自動再生でページを一度もクリックしていないときは、クリックした時点でエフェクトがかかる

## 実装方式

### 方式A（採用）：`<video>`要素をWeb Audio APIでフックする

content scriptで`AudioContext.createMediaElementSource(video)`を呼び、エフェクトを通してから`ctx.destination`に出力する。ニコ生・YouTube・Kick・Twitch・TVer・ABEMAのすべてで、ChromeとFirefoxの両方で動作を確認した。

実装上の決まりごと：
- **接続する要素を限定する**：別オリジンのメディアをCORSなしで再生している要素に接続すると、出力が無音になる。そのため、ページ自身がデータを用意している要素だけに接続する（`canAttach`）
  - `currentSrc`が`blob:`のもの（MSE）
  - `srcObject`が`MediaSourceHandle`のもの（Worker内のMSE。ChromeのKick・Twitch）
- **二重接続を防ぐ**：`createMediaElementSource()`は同じ要素に1回しか呼べない。接続済みの要素は`WeakMap`で管理する
- **無効のあいだは接続しない**：接続すると、リロードするまで元に戻せないため
- **バイパスはつなぎ替えで行う**：接続後はグラフを切らず、wet/dryのゲインのクロスフェードで切り替える。値は`setTargetAtTime`（時定数20ms）で変え、プツッというノイズを防ぐ
- **AudioContextがrunningになってから接続する**：自動再生ポリシーでsuspendedのまま接続すると無音になる。`pointerdown`と`keydown`のたびに`resume()`を再試行する
- **AudioContextは48kHzで作る**：RNNoiseもDeepFilterNet3も48kHz前提のため
- **再生開始を`playing`イベントで拾う**：`document`でキャプチャフェーズのリスナーを使う（メディアイベントはバブリングしない）。MutationObserverや`yt-navigate-finish`は使っていない
- DRM（EME）付きのコンテンツ：ABEMA（ChromeとFirefoxのWidevine）では音が取れ、EQも効いた。ほかのDRM（ハードウェアで復号するものなど）で取れるかは分からない

### 方式B（未実装）：`chrome.tabCapture`でタブ音声をキャプチャする

対象サイトはすべて方式Aで対応できたため、実装していない。方式Aが使えないサイトに対応するときの代替案として残す。

- service workerで`chrome.tabCapture.getMediaStreamId()`を取得する
- offscreen documentで`getUserMedia({ audio: { mandatory: { chromeMediaSource: 'tab', chromeMediaSourceId } } })`を使ってストリームを受け取る
- キャプチャ中はタブ本来の音が止まるので、加工後の音をoffscreen側のAudioContextで再生する
- 拡張アイコンのクリックなど、ユーザー操作を起点にする必要がある

## 音声グラフの構成

```
source ─┬─┬─ RNNoise ──────── 方式ごとのwet ─┬─ eqIn ─ EQ ─┬─ コンプレッサー ─ compWet ─┬─ リミッター ─ wet ─┬─ output ─ destination
        │ ├─ DeepFilterNet3 ─ 方式ごとのwet ─┤             └─────────────── compDry ─┘                   │
        │ └──────────────────────── nrDry ──┘                                                           │
        └────────────────────────────────────────────────────────────────────────────────────── dry ───┘
```

- **全体のON/OFF**：`wet`/`dry`で切り替える
- **ノイズキャンセルのON/OFFと方式**：方式ごとのwetと`nrDry`で切り替える
- **eqIn**：EQに入る前の音をまとめるところ。オートEQはここを分析する
- **イコライザー**：31Hz〜16kHzを1オクターブずつ、10バンドに分けている
  - 両端（31Hz、16kHz）はシェルビング、ほかはピーキング（Q=1.4、約1オクターブ幅）
  - ユーザーが変えるのはゲインだけ（±12dB）
  - ゲインの決め方
    - オートEQがオフ：設定のゲイン（`gains`。カスタムかプリセット）を使う
    - オートEQがオン：オートEQの補正量を使う。`eqPreset`と`gains`は使わずに残しておく
  - 帯域の数が変わった古い設定は、ゲインの位置がずれるのでフラットに戻す
- **音量をそろえる**：EQの後ろの`DynamicsCompressorNode`で、`compWet`/`compDry`で切り替える。下の「音量をそろえる」を参照
- **リミッター**：エフェクト側の経路の最後に常に入れ、0dBFSを超えないようにする。下の「リミッター」を参照
- **設定**：`chrome.storage.local`の`settings`キーに`{ enabled, denoise, engine, leveler, autoEq, autoStrength, eqPreset, gains }`を保存する
  - 既定値は「有効、ノイズキャンセルはオフ、方式はRNNoise、音量をそろえるはオフ、オートEQはオフ（強さは標準）、EQはフラット」
  - `autoEq`はオートEQのオン・オフ
  - `eqPreset`は`custom`（手動）、またはプリセットのidをとる
  - `autoStrength`は`gentle`（控えめ）、`standard`（標準）、`strong`（強め）をとる
  - `eqPreset`がない以前の設定は、ゲインをそのまま使えたら`custom`、フラットに戻したら`flat`とみなす
  - v0.12.0までは、オートEQを`eqPreset`の`auto`で表していた。この設定は、`autoEq`をオンにし、`eqPreset`をゲインと同じプリセット（なければ`custom`）にして読み込む

### オートEQ（試作）

`extension/audio/auto-eq.js`。EQに入る前の音（`eqIn`）を分析し、帯域ごとの長い時間の平均レベルを目安の形に近づけるゲインを求める。

- **EQの前で測る理由**：EQの後ろで測ると、自分の補正を測り直して補正が強まり続ける。前で測ればそうならない
- **分析**：AnalyserNode（FFT 8192点）で0.25秒ごとに帯域のエネルギーを測る
  - 帯域は、各中心周波数から上下に半オクターブ
  - 平均の時定数は15秒。最初のうちは単純な平均をとる
  - 帯域の合計が−60dB未満のとき（無音）は平均に入れない
- **補正の計算**：1秒ごとに行う。音が5秒分たまるまでは補正しない（0dBのまま）
  1. 125Hz〜4kHzの平均で、目安の形の高さを合わせる
  2. 帯域ごとに「目安 − 平均レベル」を求める。目安より24dB以上小さい帯域は、もともと音が入っていないとみなして持ち上げない
  3. 隣の帯域と0.2 / 0.6 / 0.2でならす
  4. 強さに応じた割合をかけ、上限で切り詰める（下の表）
- **目安の形**（31Hz〜16kHz、dB）：−8, −3, 0, 0, 0, −1, −3, −6, −9, −15
  - 中域を平らにし、高域に向かってなだらかに下げた仮の値。根拠のある正解ではなく、聞いて調整する前提
- **オン・オフと強さ**：ポップアップのスイッチでオン・オフし、オンのあいだに強さを選ぶ。強さを変えると、分析済みの結果からすぐに補正し直す。オフにすると分析を止め、もう一度オンにすると分析をやり直す

| 強さ | 補正する割合 | 下げる上限 | 持ち上げる上限（そのほか） | 持ち上げる上限（125Hz・8kHz） | 持ち上げる上限（31Hz・62Hz・16kHz） |
|---|---|---|---|---|---|
| 控えめ | 50% | 6dB | 6dB | 3dB | しない |
| 標準（既定） | 75% | 9dB | 9dB | 4.5dB | しない |
| 強め | 100% | 12dB | 12dB | 6dB | しない |

  - 両端を持ち上げないのは、声の配信で31Hz・62Hzを+3.8dB持ち上げてしまったため。低い帯域や、圧縮で削られた高い帯域を持ち上げても、こもった響きや雑音が増えるだけになる
  - 割合も段階的に変えている。割合を同じ（100%）にして上限だけを変えたときは、差が上限を超える帯域がない限り、「標準」と「強め」の結果が同じになった
- **経緯**：最初の試作は「差の75%・上限±6dB・ならしは0.25 / 0.5 / 0.25」だった。補正が±2〜5dBにとどまり控えめすぎたので、上の形に強めた
- **反映の仕方**：ゲインは時定数1秒で滑らかに変える
- **ポップアップでの表示**：オートのあいだ、ポップアップは表示中のタブのcontent scriptに1秒ごとに状態（`audio-fx:status`）を問い合わせ、補正量をスライダーに表示する
- **実測（2026-11-09、標準と強め）**：

| 配信 | 標準 | 強め |
|---|---|---|
| Kick | 500Hz −2.7dB、8kHz +4.5dB、125Hz +4.5dB | 500Hz −3.5dB、8kHz +6.0dB、125Hz +6.0dB |
| ニコ生（アニメ上映会） | 125Hz +2.0dB、500Hz −0.6dB、31Hz −3.2dB | 125Hz +3.5dB、500Hz −2.0dB、31Hz −3.7dB |

  - 割合を100%にしていた段階では、YouTubeのBBCニュース（声）で250〜500Hzを約−5.5dB、4kHzを+8.7dB補正した
- **限界**：もともと高音を控えめにした録音（ジャズなど）も、明るい音に寄せてしまう。番組の個性まで標準的な音に寄せるのは、この方式の限界

### リミッター

EQやオートEQで持ち上げても0dBFSを超えて音割れしないように、エフェクト側の経路の最後に常に入れている（素通しのdry側には入れない）。

- **作り**：`DynamicsCompressorNode`をリミッターとして使う。threshold −3dB、knee 0、ratio 20、attack 0、release 0.1秒
- **メイクアップゲインの打ち消し**：このNodeは、0dBの入力に対するゲインの逆数の0.6乗を、自動のメイクアップゲインとしてかける。この設定では1.71dBになる
  - 直後のGainNodeでこの分を打ち消し、しきい値より小さい音は変えないようにしている
  - コードでは、設定値から式で計算している（実測とも一致した）
- **正弦波での測定**（100Hz、OfflineAudioContext）：

| 入力 | 出力のピーク |
|---|---|
| −20dB、−6dB | そのまま |
| +12dB | −1.95dBFS |
| −30dBから+12dBへ跳ね上がる音 | −1.35dBFS |

  - しきい値を−1dBにすると、跳ね上がる音で+0.4dBFSになったので、−3dBにした
- **実際の配信での測定**（YouTubeの音量の大きい音楽、プレイヤーの音量を最大にした）：

| EQ | EQの後のピーク | 出口のピーク |
|---|---|---|
| フラット | −0.2dBFS | −2.7dBFS |
| 低音強調（+8dB） | +0.6dBFS | −3.0dBFS |
| 小音量・夜間 | +0.9dBFS | −2.9dBFS |
| 全帯域+12dB | +11.5dBFS | −1.4dBFS |

  - リミッターを入れる前は、以前の低音強調（+5dB）でもEQの後で+1.9dBFSになり、音割れしていた
  - 音量の大きい配信では、フラットのときでも−3dBFSを超える一瞬のピークを2dBほど抑える。ふだんの大きさの音は変わらない

### 音量をそろえる

`DynamicsCompressorNode`は、圧縮した分に応じて自動で音量を持ち上げる（メイクアップゲイン）。そのため、大きい音は抑えられ、小さい音は大きくなる。後ろには常にリミッターが入る。

| 強さ | threshold | knee | ratio | attack | release | 1kHzの正弦波で測った入力 −50dB / −3dB に対する出力 |
|---|---|---|---|---|---|---|
| 弱 | −24dB | 12dB | 2 | 10ms | 250ms | −44.7dB / −6.3dB |
| 中 | −32dB | 12dB | 4 | 5ms | 250ms | −38.2dB / −10.5dB |
| 強 | −40dB | 10dB | 8 | 3ms | 250ms | −31.2dB / −15.3dB |

- **音割れ**：どの強さでも出力は0dBFSを超えなかった。0dBと−20dBが入れ替わる信号でも、いちばん大きくて−1.2dBFS
- **小さい音を持ち上げる副作用**：「強」は小さい音を大きく持ち上げるので、背景の雑音も持ち上がる。ノイズキャンセルと併用すると抑えられる
- **急に大きな声が入ったとき**（2026-11-11、Chrome、声に似せた音で測定。リミッターを含む）：大きな声が普通の声より小さくなることはなかった。大きな声のあと、0.1〜0.2秒で普通の声の大きさに戻った

| 入力（普通の声 → 大きな声） | 弱 | 中 | 強 |
|---|---|---|---|
| −26dB → −6dB | −22.0 → −13.0dB | −21.4 → −15.5dB | −23.3 → −20.0dB |
| −38dB → −6dB | −32.7 → −13.0dB | −27.0 → −15.5dB | −25.9 → −20.0dB |
| −26dB → 音割れした大きな声（−1dB） | −22.0 → −4.7dB | −21.4 → −9.0dB | −23.3 → −13.7dB |

- **「大きな声のところで極端に小さくなった」という報告**（2026-11-11、ニコ生、強）：上の測定では再現しなかった。原因は未確認。考えられるのは次のどれか
  - PCのラウドネス等化（Windowsのサウンドの「拡張」）。大きな音に反応して音量を下げ、ゆっくり戻す
  - ノイズキャンセルを有効にしていた場合、大きな声や音割れした声を雑音と判定して消した
  - 配信者側の音声処理（マイクの自動音量調整、配信ソフトのコンプレッサーやノイズ除去）
  - 切り分けるには、同じ場面をタイムシフトで再生し、拡張のON/OFFで聞き比べる

### ノイズキャンセル

**方針**：RNNoiseとDeepFilterNet3の両方を入れ、ユーザーがポップアップで選ぶ。既定はRNNoise。

- 2026-11-09の聞き比べでは、違いはわかりにくかった
- DeepFilterNet3の強みは、雑音の多い配信で出ると考えている

| | RNNoise | DeepFilterNet3 |
|---|---|---|
| パッケージ | `@sapphi-red/web-noise-suppressor` 0.4.1 | `@workadventure/noise-suppression` 0.2.0 |
| 遅延 | 約13ms（640サンプル） | 約71ms（実測70.7ms） |
| CPU（i7-8700K、1コアに対する割合） | 約3.7%（ステレオ） | 中央値17〜21%、95パーセンタイル18〜31%（プロセッサの負荷レポート） |
| チャンネル | チャンネルごとに処理。入力は2ch（ステレオ）にそろえる | モノラルにまとめて処理し、モノラルで出す（EQに入るところで左右に広がる） |
| ファイルサイズ | WASM 約154KB | WASM 14.6MB + モデル 8MB |
| 準備中の出力 | 無音になるので、ノードを作ってから0.15秒待って切り替える | 準備ができるまでは入力をそのまま出す（`bypassUntilReady`） |

ノードの作り方と止め方：
- **作るとき**：その方式を選んだときにノードを作る。ノイズキャンセルを有効にしたとき、または方式を切り替えたとき
  - 準備中や作れなかったときは`nrDry`（素通し）にする
- **止めるとき**：使わなくなった方式は、出力を0.2秒でフェードアウトしてから止める
  - RNNoiseは`destroy`、DeepFilterNet3は`dispose`で止める
  - もう一度選ばれたら作り直す。WASMやモデルは読み込み済みなので速い
- **準備中に切り替えられたとき**：準備が終わった時点で、使わずに止める

それぞれの読み込み方：
- **RNNoise**：ワークレット内では`fetch`が使えないので、WASMはcontent scriptで取得し、`processorOptions.wasmBinary`で渡す
  - 128サンプル単位の入力を、1920サンプルのリングバッファで480サンプルのフレームに組み替えている
- **DeepFilterNet3**：パッケージの`createDeepFilterNetAudioWorklet()`は使わず、ノードを自分で作る
  - Firefoxでは、この関数がワークレットに渡す`WebAssembly.Module`をページ側にコピーできないため
  - ワークレットに渡す設定（`DEEPFILTERNET_OPTIONS`）は、この関数（0.2.0）の既定値と同じにしている。パッケージを更新したら、`dist/deepfilternet.js`の設定が変わっていないかを確かめる
  - WASMは、Chromeではcontent scriptでコンパイルした`WebAssembly.Module`を渡す（14.6MBをワークレットの音声処理のスレッドでコンパイルさせると、音が途切れるおそれがあるため）。Firefoxではバイト列で渡し、ワークレットでコンパイルさせる（準備まで約0.3秒）
  - 以前は関数を動的importして使っていた。そのときは、パッケージが`import.meta.url`から作るURLが拡張の固定URLになり、`use_dynamic_url`を有効にしているとページから取得できなかった（「Failed to fetch」）ので、`getURL`の動的URLを明示的に渡していた

## 検証

### 自動検証（`tools/verify.js`）

インストール済みのChromeを、一時プロファイル・ヘッドレス・ミュートで起動する。`extension/`を読み込んで配信を再生し、ポップアップを実際に操作して、次の13個の設定を順に測る（v0.12.0までは、3を除く12個）。

1. オートEQ・標準（手動のEQをニュースにしてからオンにする。20秒待って、分析が落ち着いてから測る）
2. オートEQ・強め（強さを変えて4秒待つ）
3. オートEQをオフに戻す（手動のEQのニュースに戻ること）
4. EQ有効
5. 全体を無効にする（素通し）
6. ゲインを変えて有効に戻す
7. プリセット（ニュース）
8. プリセット（低音強調）：大きく持ち上げても、リミッターで0dBFSを超えないこと
9. 音量をそろえる（強）
10. ノイズキャンセル有効（RNNoise）
11. ノイズキャンセル有効（DeepFilterNet3）
12. RNNoiseに戻す（止めた方式を作り直す）
13. すべて無効に戻す（EQだけ有効）

オートEQを最初に測るのは、時間がかかり、YouTubeでは再生開始から約40秒で動画が止まることがあるため。

拡張のcontent scriptと同じ実行環境（isolated world）で、音声グラフの入口と出口にAnalyserNodeを付けて判定する。

- **パラメータ**：各フィルタのゲイン、wet/dry、方式ごとのwet、`nrDry`、`compWet`/`compDry`が設定どおりか
  - ポップアップのスライダーは、画面上の位置ではなく帯域の番号（`data-band`）で選んで動かす
  - 全体がOFFのあいだはほかの欄を操作できないので、先にONにしてから設定し、OFFにするのは最後にする
- **ポップアップの操作の制限**：全体がOFFのとき、「有効」のスイッチ以外の欄を操作できなくなっているか（ONのときは操作できるか）
  - プリセットは選択欄で選び、期待値はポップアップの`Settings.PRESETS`から取る
- **オートEQ**：分析が終わっているか、補正量が強さごとの上限（控えめ±6、標準±9、強め±12dB）に収まっているか、フィルタのゲインが補正量に追いついているか（1.5dB以内。内容がよく変わる番組では、補正量が1秒に0.5dB以上動くことがあるため）
  - オートEQ以外のときは、オートEQの分析が止まっているかも確かめる
  - 目安からのずれ（補正前と補正後）を表示する
- **使っていない方式が止まっているか**：選んでいない方式のノードが残っていないか
- **周波数特性**：EQの「出口 − 入口」が、`getFrequencyResponse`から計算した期待値と1.5dB以内か。62Hz、1kHz、4kHz、12kHzで測る
  - 入力の最も強い成分より50dB以上弱い帯域は判定しない
  - ノイズキャンセルや音量をそろえる、オートEQが効いているときは判定しない
  - 測定中にリミッターが1dB以上効いたときも判定しない
- **無音でないか**：出力が完全な無音（CORSやWASMの読み込み失敗）になっていないか
- **音割れしていないか**：出力のピークが0dBFS（1.0）を超えていないか
- **判定できないとき**：次の場合はスキップとして扱い、次の配信で測り直す
  - 動画が止まっているなど、入口から無音のとき
  - 測っている途中で動画が止まったり、再生位置が戻ったりしたとき（広告など）

2026-11-09の時点で、3サイトとも12パターンすべてOK（期待値との差は0.2dB以内）。

- オートEQは、音が5秒分たまるまで補正しない。番組の冒頭など音が小さい時間が続くと、20秒待っても分析が終わらず、NGになることがある（ニコ生で1回あり、同じ番組で測り直してOK）

- YouTubeは、何本かの配信で途中から動画が止まって測れなかった。止まらなかった配信でOKを確認した
- 止まる原因は、下の「自動再生」を参照

2026-11-10に、Twitchも12パターンすべてOK（`MediaSourceHandle`で再生）。TVer（見逃し配信とリアルタイム配信）とABEMA（放送中のチャンネル）も12パターンすべてOK。

2026-11-11に、オートEQをスイッチにした版（v0.13.0）で、Twitchの13パターンすべてOK（Firefoxの検証もOK）。

- **TVerのアンケート**：検証では回答せず、「閉じる」で閉じてから、スクリプトで`play()`を呼んで再生する（`sites.js`の`dismiss`）。閉じたあとに再生ボタンを押すと、またアンケートが出る
- **TVerの再生開始**：トップページを開いたあとだと、`play()`から約5秒、プレイヤーが動画を止めたままにする（広告の準備と考えている）。そのため、再生が始まるまで最大10秒待つ（`waitPlaying`）
- **TVerで1回だけ出たNG**：オートEQのゲインが補正量に追いつかない（ドラマ）、EQの周波数特性が1.5dB以上ずれる（リアルタイム配信）が、それぞれ1回あった。測り直すとOKだった
- **ABEMAのビデオ**：本編の前に広告が流れ、検証ツールのクリックが広告に当たるので、検証ツールには入れていない。別のスクリプトで、広告が終わってから本編をクリックし、拡張がつながってEQが効くことを1回だけ確かめた（62Hz：期待−6dB → 実測−5.5dB、4kHz：期待+4dB → 実測+3.8dB）

### Firefoxの自動検証（`tools/verify-firefox.js`）

インストール済みのFirefoxを、一時プロファイル・ヘッドレスで起動する（WebDriver BiDi）。テスト用の仕組みを足した拡張のコピーを一時的なアドオンとして読み込み、配信を再生して次を確かめる。

1. **接続**：video要素に接続され、AudioContextがrunningか
2. **EQ**：フィルタのゲインと周波数特性（Chromeと同じ判定）
3. **ノイズキャンセル**：RNNoiseとDeepFilterNet3のノードが準備でき、切り替わり、使っていない方式が止まっているか
4. **ポップアップ**：プリセットの選択肢がそろっているか、ニュースを選ぶとEQに入るか、配信のタブに状態を問い合わせられるか
5. **リミッター**：メイクアップゲインの打ち消し（1.71dB）がChromeと同じか、+12dBの入力でも−1dBFSを超えないか

Chromeの検証との違い：
- **測り方**：CDPが使えないので、テスト用のcontent script（`tools/firefox-probe.js`）をコピーにだけ足し、ページから`postMessage`で測定を頼む
- **音量**：ミュートせず、動画の音量を0.01にして測る（下の「Firefox対応」を参照）。そのため、小さい音を分析に入れないオートEQは確かめていない

## 検証で分かったこと

### AudioWorkletの読み込み（content scriptから）

| 読み込み方 | ニコ生（CSPヘッダーなし） | YouTube（厳しいCSP） |
|---|---|---|
| 拡張内のURLを直接指定（`web_accessible_resources`に登録） | OK | OK |
| 同上（登録なし） | NG | NG |
| Blob URL / data: URL | OK | NG（CSPで止められる） |

- **採用した方法**：`web_accessible_resources`に登録し、`chrome.runtime.getURL`で直接読み込む
- **`use_dynamic_url: true`も設定している**：`getURL`がセッションごとに変わるURLを返すようになり、ページ側から拡張の固定URLにアクセスできなくなることを確認した
- **WASMの実行**：ワークレット内でのWASMの実行は、ニコ生・YouTube・Kickのどれでもページのcontent security policyに止められなかった
- **YouTubeでのみ出るログ**：content scriptからWARのファイルを`fetch`すると、`Unsafe attempt to load URL ...`というsecurityログが出る。取得自体は成功している
  - 固定URLでも出る
  - ニコ生では出ない。Kickは未確認

### ノイズキャンセルのCPU負荷と遅延（2026-11-09、i7-8700K 6コア12スレッド）

- **RNNoise単体**：ステレオの音声1秒を処理するのに約36.5msかかる。CPU 1コアの約3.7%で、タスクマネージャーの表示（全スレッドに対する割合）では約0.3%
  - 測り方：ニコ生のページのcontent scriptで、OfflineAudioContextに30秒分のステレオ音声を流し、RNNoiseあり・なしの処理時間を比べた
- **再生中の実測**：Chromeのプロセス別CPU使用率は、同じ状態でも測るたびに10ポイント以上揺れた。そのため、RNNoiseの分は見分けられなかった
- **DeepFilterNet3**：3サイトで再生中に測った
  - CPU：プロセッサの負荷レポートで、中央値は実時間の17〜21%。タスクマネージャーの表示では約1.7%
  - 遅延：入口と出口の波形の相互相関で70.7ms
  - 読み込み：WASMのコンパイルを含めて81〜229ms。準備ができるまで336〜380ms
  - 効き方：環境音だけの配信（ニコ生の馬房の定点カメラ）で、約45dB下がった（同じ配信でRNNoiseは約8dB）
- **拡張のページでの注意**（方式Bのoffscreen documentでノイズキャンセルを使うときは要確認）
  - 拡張のページ（ポップアップなど）では、RNNoiseのWASMが動かず、出力が無音になった。原因は拡張のページのCSPと考えている（未確認）
  - 拡張のページで`chrome.runtime.getURL`のURLを使うと、`use_dynamic_url`による動的URLになり、ワークレットを読み込めなかった。拡張のページからは相対パスで読み込む

### 自動再生

- ニコ生：自動再生が止められる。再生ボタンのクリックで始まる
- Kick：ミュートで自動再生される。ミュート中は音がないので、クリック待ちのあいだに無音の時間ができることはない
- YouTube：ヘッドレスでは、画面中央のクリックでは再生されないことがあった。再生ボタンでは再生された
- YouTube：ヘッドレス・未ログインでは、多くの配信で、再生開始から約40秒で動画が一時停止し、再生位置が0秒に戻った
  - 拡張のせいではない。ノイズキャンセルを有効にした場合（38秒）と、何もしない場合（39秒）で同じように起きた
  - 広告表示中の印（`#movie_player.ad-showing`）は付いていなかった
- Twitch：音ありで自動再生される
- TVer：見逃し配信は自動再生されない（アンケートの回答が必要）。リアルタイム配信は音ありで自動再生される
- ABEMA：放送中のチャンネルは音ありで自動再生される。ビデオは広告のあとで本編が自動で始まる

## Firefox対応

2026-11-10に対応した。manifestはChromeと同じものを使う（分けていない）。

### 実装の違い

Chromeと同じコードで動くようにしている。Firefoxでだけ違う動きをするのは次の2点。

- **ワークレットに渡すオブジェクト**：Firefoxでは、content scriptで作ったオブジェクトをそのまま`AudioWorkletNode`の`processorOptions`や`port.postMessage`に渡すと、`DataCloneError`になる。content scriptのオブジェクトはページ側からは見えない扱いのため
  - `cloneInto(obj, window)`でページ側にコピーしてから渡す（`audio-graph.js`の`toPage`）。Chromeには`cloneInto`がないので、そのまま渡す
- **DeepFilterNet3のWASM**：`WebAssembly.Module`は`cloneInto`でコピーできない（unsupported value type）。Firefoxではバイト列で渡し、ワークレットの中でコンパイルさせる（「ノイズキャンセル」を参照）

### 分かったこと

- **ミュートと音量**：Firefoxでは、タブのミュートと動画の音量が、Web Audioに入る手前でかかる。ミュートすると拡張に届く音も無音になる。Chromeでは、動画の音量は入る手前でかかるが、`--mute-audio`で起動しても拡張に届く音は無音にならない
  - 自動検証では、ミュートせず動画の音量を0.01にして測っている
  - `media.volume_scale`を0にしても、拡張に届く音が無音になった
  - `media.cubeb.force_null_context`（音声出力をなくす設定）を使うと、Web Audio自体が動かなくなった
- **Kick・Twitchの再生方式**：Firefoxでは`blob:`になる（Chromeでは`MediaSourceHandle`）
- **リミッター**：`DynamicsCompressorNode`が自動でかけるメイクアップゲインは、Chromeと同じ値（1.71dB）だった。打ち消し用のGainNodeはそのままでよい
- **WebDriver BiDiの制限**：拡張の内部URLを開けない。内部扱いのタブは、前面に出すことも読み込み直すこともできない

### 常用するには

- `about:debugging`の一時的なアドオンは、Firefoxを再起動すると消える
- 通常のFirefoxで入れたままにするには、署名が要る。自分用なら、AMOに「自己配布（unlisted）」で出して署名だけ受ける方法がある。Developer EditionかNightlyなら、`xpinstall.signatures.required`をfalseにして署名なしで入れられる
- 署名するときに決めること・確かめること
  - 拡張のID（`browser_specific_settings.gecko.id`）を決める。Chromeでは、このキーがあると「認識できないキー」の警告が出る（動作には影響しない）。気になるなら、そのときにmanifestを分ける
  - AMOへの提出で`data_collection_permissions`（データ収集の申告）が必要かを確かめる（未確認）

## 録画拡張との関係

2026-11-09に録画拡張のコードを確認し、録画の取り方を再現して測った。

- **接続の取り合いがない**：録画拡張は`createMediaElementSource`を使っていない
- **干渉する処理がない**：ページ側で動くスクリプト、メディア関連の仕組みの書き換え、AudioContextの使用はどれもない
- **結論**：録画が失敗する、無音になる、エラーになる、といった悪影響はない

| 録画の種類 | 音の取り方 | 録画に入る音 | 確認 |
|---|---|---|---|
| コメントなし / コメントあり | `video.captureStream()`（`utils/recording-source.ts`） | 元の音（EQもノイズキャンセルもかからない） | 実測（ニコ生・YouTube） |
| 画面録画 | `getDisplayMedia`のタブ音声（`utils/screen-capture.ts`） | エフェクト後の音のはず | 未確認 |

- **captureStreamの測定**：先に`captureStream()`を取得してからこの拡張が接続した場合（録画拡張と同じ順番）も、元の音だった
- **captureStreamの音量**：プレイヤーの音量をかける前の音になる。音量0.5のとき、拡張の入口より約6dB大きい
- **画面録画が未確認の理由**：ヘッドレスのChromeでは、拡張がなくてもタブ音声が無音になり、測れなかった。タブ音声はタブが出す音をすべて取る仕組みなので、エフェクト後の音が入ると考えている
- **録画にエフェクトを入れたい場合**：コメントなし・コメントありの録画に入れるには、録画拡張側の変更が必要になる。具体的には、拡張どうしが連携して、録画拡張がこの拡張の出力から音を受け取るようにする

## 既存の拡張の調査（2026-11-09）

Chromeウェブストアの音声系の拡張を調べた。主な38件は、パッケージ（CRX）の中身（manifestとコード）まで確認した。

**分かったこと**
- **3つの機能を1つで持つ拡張はない**：EQ・AIノイズ除去・音量の平準化（AGCやコンプ）の組み合わせ
  - 近いのは ClearSound（15バンドEQ＋RNNoise＋リミッター。音量の平準化はない。ユーザー50人）
  - ストア未公開では Clarify（GitHub。AIノイズ除去＋AGC＋EQ＋コンプ＋リミッター。タブの音を取る方式）
- **EQとコンプの組み合わせは多い**：最大手は Equalizer for Chrome browser（50万ユーザー、10バンドEQ＋コンプ、タブの音を取る方式）
- **AIノイズ除去**：リスナー向けは少数
  - DAMIKO の AI Noise Cancellation For Listeners（独自のSDK）
  - ClearSound（RNNoise）
  - DeepFilterNet を使った拡張は見つからなかった
  - 「AIノイズ除去」をうたっていても、中身は普通のフィルタやゲートのものが多い（Audio Enhancer Pro、Hearably など）
- **オートEQ**：番組の音に合わせて補正する拡張は見つからなかった
- **ニコ生向け**：音声エフェクトの拡張は見つからなかった
  - ニコ生専用ツールの NicoViewer は、この拡張と同じく`createMediaElementSource`でニコ生の動画をつないでいる
- **2つの方式の弱点**
  - タブの音を取る方式（tabCapture）：レビューで多い不満は、全画面がウィンドウの中に限られる、タブごとに有効にする必要がある、キャプチャの競合がある、など。この拡張はvideo要素をつなぐ方式なので当てはまらない
  - video要素をつなぐ方式：別オリジンの要素や、別オリジンのiframeの中の要素には使えない
  - 最近は、video要素をつなぐ方式を優先し、だめならタブの音を取る、という併用型が増えている

**差別化になりそうな点**
- EQ・本物のAIノイズ除去・音量の平準化を1つで持つ
- AIノイズ除去を2種類（RNNoise / DeepFilterNet3）から選べる
- オートEQ
- ニコ生・Kickに対応している
